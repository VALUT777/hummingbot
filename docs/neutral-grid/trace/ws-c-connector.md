Engine/store contract of the scanner:

- `new_trades`/`new_orders` are rows not yet committed (per `committed_payload`); committing them is idempotent by key.
- `trades_high_water`/`orders_high_water` are returned **only when `complete`**. The engine commits them in the same SQLite transaction as inbox rows, dedupe keys and ledger transitions (NG-HIST-002). The scanner never writes durable state; its in-flight pagination cursor lives only in memory.
- Stream names are `"trades"` / `"inactive_orders"`; the trade dedupe key is `ExchangeTradeRow.dedupe_key(port.domain)`; the order key is `order_dedupe_key(port.domain, row)`; stored payloads must be the `*_payload_fingerprint` strings.
- `incomplete_reason` values: `in_progress`, `backoff`, `repeated_cursor:*`, `malformed_cursor:*`, `schema_error:*`, `page_fetch_error:*`, `empty_page_with_cursor:*`, `oversized_page:*`, `ordering_violation:*`, `conflict`, `retention_gap`. Anything but `complete=True` blocks new exposure and terminal release.
- Malformed-cursor detection is structural (non-string, whitespace/control chars, > 4096 chars). A venue- or fake-specific undecodable cursor (e.g. the FakeExchange's `%%%not-base64%%%`) shows up as that endpoint's page error, which is still `complete=False`.

## Decisions

- **Outcome classification** (`submit_with_client_id`/`cancel_with_client_id`): `NOT_SENT` only on returns that happen before the signer is invoked (CID type/bounds `[1, 2**48)`, side, LIMIT/LIMIT_MAKER only, positive exact price/amount at venue precision with no silent quantization, expiry type, market availability, signer present). `ACCEPTED` only for `error is None` and code 200. Everything else is `UNKNOWN`, including raised exceptions, timeouts, error strings and non-200 codes. `DEFINITIVE_REJECT_ZERO_FILL` is **never emitted**. The SDK documents no definitive-rejection codes and collapses local signing errors and HTTP 400 into one tuple. The code comment cites this.
- **CID reuse**: a CID already in the tracker (live or cached) returns `UNKNOWN duplicate_client_order_id_in_flight` without sending. Across restarts, only the engine can enforce "no re-send": `SUBMIT_UNKNOWN` outbox rows must never be re-dispatched.
- **Nonce**: secondary corroborating field only (stored as a string on `ExchangeOrderRow.nonce`); no pre-send nonce exists in SDK 1.1.4.
- **Order tracker**: CID orders are registered before the signer call, move to OPEN on ACCEPTED and to PENDING_CANCEL on an accepted cancel, and receive WS updates and fill events as usual. They are **excluded from the legacy per-order REST status poll and the `recentTrades` poll**. Those cost 300–400 weight per order per poll, and about 60 grid orders would exhaust the 18000/min pool and starve the authoritative scanner. The engine reconciles them from history and calls `release_history_reconciled_order`. Legacy orders are polled exactly as before.
- **Throttling**: history pages go through `_api_get` with explicit `limit_id` (inactive 100 + pool, trades 600 + pool). CID submit/cancel also enter `SEND_TX_LIMIT`, which on Standard is linked to the pool at weight 6.
- **Ordering assumption**: the scanner requires non-increasing timestamps on both streams, and non-increasing numeric trade ids on trades. The inactive-orders timestamp field is configurable (`order_timestamp_field`, default `timestamp`). A mismatch fails closed as `ordering_violation`.
- **Weight budget math (Standard)**: steady scan = 1 trades page + 1 inactive page = 700. With active orders (300) and account (300) per engine tick, a 5 s cadence costs 12 × 1300 = 15600/min (87 % of 18000). Recommended: steady history cadence ≥ 10 s plus coalesced WS wakeups (`min_wake_interval_s=1`), giving about 7800/min. The default scanner `weight_budget=1400` allows two pages of each endpoint per call.

## Open risks

1. **Venue idempotence**: none documented for `client_order_index`. Re-sending the same CID is refused; an UNKNOWN submit stays UNKNOWN (reservation kept) until an exact CID/order row or trade appears in history, or until a manual audit.
2. **Definitive zero-fill reject**: no documented evidence at transport level. Zero-fill terminal is proven only via history, e.g. an inactive row `canceled-post-only` with `filled_base_amount=0` plus full scan plus settlement (`test_zero_fill_terminal_requires_the_same_proof`). Consequence: some locally-invalid sends (SDK signing errors) hold reservations until history settles.
3. **accountInactiveOrders sort key is undocumented**. If the venue does not return rows newest-first by the chosen timestamp field, scans never complete. That is safe but blocks the engine. It needs a read-only operator verification; no live call was made here, because live API use is not authorized for this session.
4. Timestamp units are inferred by magnitude (s/ms/µs/ns), following the existing connector convention. An empty `next_cursor` (`""`) is treated as the natural end. Cursor lifetime between ticks is unknown; an expired cursor becomes `page_fetch_error`, and the walk restarts after backoff.
5. Retention-gap detection works in two ways: the committed high-water row is no longer served at the natural end, or an optional configured horizon is exceeded. It cannot tell a venue purge from venue data loss, and both are reported as `retention_gap`.
6. Liquidation, deleverage and market-settlement trades are kept as own legs (their `type` is in `raw_json`). If they carry no own CID, the engine must treat them as unknown owned fills and freeze.
7. The SDK default `order_expiry=-1` (28 days) also applies to post-only entries, so entries expire as well (`canceled-expired` in history). Entry renewal is an engine policy.
8. `best_bid_ask`/`mid_price` come from Hummingbot's float order book. They are reference prices only, never ids, quantities or ledger values. `TradingRules.max_base` is `None`, because the connector's market info does not expose it.
9. Pre-existing and not changed: `SEND_TX_LIMIT` is `RateLimit(limit=360, weight=1)`. Its own bucket therefore admits 360 sendTx/min instead of Standard's 60; the pool link at weight 6 caps it at 3000/min.
10. Stopping per-order polling for CID orders means the tracker state of those orders follows WS only. If the engine never calls `release_history_reconciled_order`, they stay in `in_flight_orders`.
